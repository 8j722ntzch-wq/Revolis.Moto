## Первый проход после подтверждения подписки

1. Вызвать `whoami` и сверить аккаунт, команду, план и seat. Этот диагностический инструмент освобождён от лимита чтения. Не повторять запрос макета, пока прежняя причина отказа не изменилась.
2. Использовать точные `fileKey` и `nodeId` из `design/figma-source.json`. Если пользователь переместил/дублировал файл и ссылка изменилась, взять новую ссылку от него.
3. Загрузить актуальный навык Figma Design to Code и вызвать `get_design_context` с Astro, HTML/CSS/TypeScript и включённым screenshot. Указать `skillNames` согласно прочитанному навыку.
4. Если ответ разреженный, сопоставить реальные дочерние узлы со снимком и получить полноценный контекст секций. Соблюдать текущий лимит частоты; не запрашивать всю страницу повторно без причины. Если snapshot отсутствует, получить `get_screenshot` до вёрстки.
5. Записать фактические размеры, время получения и реальные section IDs. Сохранить необходимые данные контекста без токенов и краткоживущих подписанных ссылок. Показатели предыдущего обсуждения повторно сверить.
6. Скачать оригинальные ресурсы строго указанным Figma способом, заполнить реестр, затем выполнить `npm run design:check`.

Образец первого запроса, а не команда для выполнения до покупки:

```json
{
  "fileKey": "JkXOsnFvWZmMab1VYjVQAJ",
  "nodeId": "1:13203",
  "clientFrameworks": "astro",
  "clientLanguages": "html,css,typescript",
  "skillNames": "resource:figma-design-to-code",
  "excludeScreenshot": false
}
```

## Как заполнять реестры

В `design/figma-source.json` изменить `status` на `captured` только после получения текущего контекста; указать ISO `capturedAt`, реальные `frame.width` и `frame.height`. Каждая запись `sections` содержит фактические `nodeId`, `name`, `contextQuality: "high-fidelity"`, `contextFile` с путём `design/context/<имя>.json`. Ответы с неполными данными не отмечать как high-fidelity.

В `design/assets.json` изменить `status` на `imported` только после получения ресурсов. Каждая запись содержит:

| Поле | Содержание |
| --- | --- |
| `id` | Уникальное понятное имя ресурса |
| `nodeId` | Реальный исходный узел Figma |
| `kind` | `source-image`, `exported-svg` либо `exported-raster` |
| `localPath` | Непустой файл внутри `public/assets/` |
| `slots` | Массив мест использования: реальный `nodeId` слоя и `sectionNodeId` секции |

Для каждого ресурса при вёрстке дополнительно фиксировать в записи `callsites` (компоненты), исходные размеры и параметры размещения. Проверка скриптом охватывает только наличие исходных данных, файлов и связь с указанными узлами. Соответствие самих данных Figma, все видимые слои, callsites и фактическую геометрию проверять отдельно.

## Порядок вёрстки

1. Токены и шрифты из текущего макета; основной контейнер и кнопки.
2. Header, Hero, ModelCard и секция моделей. Контрольная сверка при ширине исходного фрейма.
3. Преимущества, финансирование, тест-драйв и документы.
4. Прокат, FAQ, финальный CTA и Footer в порядке актуального макета.
5. Якоря, контекстные диалоги, раскрытие FAQ, документы, телефонные ссылки, переход на прокат и возврат наверх.

## Критерии визуальной проверки

| Область | Что сравнивать |
| --- | --- |
| Геометрия | Ширина контейнера, высоты секций, поля, интервалы, сетка, отсутствие горизонтального переполнения на Desktop |
| Типографика | Семейство и начертание, размер, line-height, letter-spacing, регистр, переносы строк |
| Изображения | Точный ресурс, пропорции, кадрирование, порядок слоёв, прозрачность и положение |
| SVG | Intrinsic width/height и viewBox, отсутствие растяжения из-за общих CSS-правил |
| Оформление | Цвета, фон, градиенты, границы, тени, скругления |
| Интерактивность | Hover/focus, Tab/Enter/Space, Escape и возврат фокуса из диалога, раскрытие FAQ |
| Формы | Валидные и ошибочные данные, недоступный endpoint, отсутствие ложного успеха, контекст CTA |

При 1470 px (если актуальная ширина не изменилась) проверяется соответствие макету; при 1366 и 1920 px — поведение Desktop. Условия мобильного расположения до мобильного макета не утверждаются. Проверка браузером ещё не выполнена; отсутствие инструмента браузера не подменять заявлением о визуальной проверке.

## Граница готовности

Успешная сборка технической основы не означает готовности главной. Завершение Desktop требует текущего дизайна, всех оригинальных ресурсов, реализации секций, проверки интерактивности и сопоставления с макетом. Публикация и подключение обработки заявок остаются отдельными действиями после завершения подготовки.
